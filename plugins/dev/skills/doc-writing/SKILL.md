# Doc writing

A document holds the content only: rules, values, options, facts, decisions.

## Content
- Before creating a doc, list the folder where such docs live (project info) and read the ones on the topic; extend the one that covers it, a new doc only when none does.
- Only what readers need and what will not go stale. Link folders instead of lists or current status.
- Write so it reads one way only. Give locations as tab, table title, row, column name, and value, in sentences.

## No meta text
Never in the document; text about the doc, the reader, or the work instead of the subject:
- Asks to the reader: 「정해 주세요」, 「골라 주세요」, 「코멘트로 알려 주세요」.
- How it was made or understood: 「~로 이해했습니다」, 「요청하신 내용」.
- Labels on values: 「임시값」, 「현재 X 값」, 「(초안)」.
- Code or asset names in headings.
- Cross-refs: 「3번 참고」, 「결정 8로 정리」.
- Notes that another doc must change.
- 「확인 못 함」 in tables.
- Personal reasons in minutes.

Where it goes instead:
- Open questions: the chat reply or a decision card. Options themselves stay as content (A안, B안 and what differs).
- Temporary values: written plainly; which are temporary goes in the chat report, or where the format asks for it (PR open-design-values section, project info).
- Answers to a comment: a reply in that thread.

## Several writers
- Before adding a section, read the doc's latest version. Edit the section that covers the topic; never add a second one.

## Check
Before handing a document over and after every edit, reread each heading and sentence against the lists above; delete or move what fails.
